---
description: Draft a pull request message and optionally open a draft PR
argument-hint: "[base branch; defaults to main]"
---
Draft a PR for the current branch against ${1:-main}. Follow repository instructions over this template.

First run `git rev-parse --show-toplevel`, `pwd`, `git branch --show-current`, `git status --short`, and `git log --oneline -5`. Check for a repository PR template under `.github/**/pull_request_template*.md` or `docs/pull_request_template*.md` (case-insensitive), including the usual uppercase and template-directory variants. Prefer the remote-tracking ref `origin/${1:-main}` over the local base branch for comparison: inspect `git diff origin/${1:-main}..HEAD` and `git log origin/${1:-main}..HEAD`. Confirm the remote-tracking target is an ancestor of `HEAD`; otherwise the double-dot diff includes differences from the target that may not belong to this PR, so inspect the merge-base diff before drafting. Check that the remote-tracking ref exists and compare its age with the remote if freshness matters. If it is absent or stale, fetch only with permission when needed; do not fall back silently to a stale local branch. Also inspect intended uncommitted changes; do not silently describe them as if they were already in the PR. If the base is missing or the branch state makes the comparison misleading, stop and ask.

Before drafting or updating the PR body, ask the user brief questions about *why* the change exists unless the motivation and concrete use cases are already explicit. Use the repository template if one exists. In the Problem section, explain what the current system does or cannot do, why that matters to a specific user or operational workflow, and any longer context needed to understand the problem. A useful shape is: “X does not provide Y. We need Y to [specific task or decision].” Do not substitute a generic need for reusable infrastructure for the use case it serves. In the Solution section, describe what this PR adds, why it addresses the problem, and how it fits into the larger effort; distinguish benefits delivered now from those that depend on later PRs. Include relevant deployment order and limitations without turning the body into an implementation walkthrough. If there is no repository template, use concise Why/Summary bullets and, only when useful, a compact Validation section for change-specific scenarios, risks, or manual checks. Do not list routine typecheck, lint, or standard test runs as a test plan. State missing verification plainly; never invent test results. Call out breaking changes and dependencies where applicable. Choose a concise title using the repository's convention; in the Vercel API monorepo prefix it with the exact affected package name from `package.json` in brackets.

Write the proposed body under `<repo-root>/.scratch/pr-drafts/<NAME>.md`. Use the Linear ticket ID as `<NAME>` when one is known (for example, `ESP-1616.md`); otherwise use a brief 2–5-word kebab-case description of the PR (for example, `http-traffic-minute-facts.md`). Determine `<repo-root>` with `git rev-parse --show-toplevel` and create `.scratch/pr-drafts/` if needed. If the chosen file already contains user work, do not overwrite it without permission. Do not use or modify `DRAFT_MSG`. Use the file edit/write tool rather than shell redirection to write the body. Display the draft and its path for review, then ask: "Submit as draft PR?" If declined, leave the draft untouched for manual editing.

If approved, check `git rev-parse --abbrev-ref --symbolic-full-name @{u}` and compare the local branch with its upstream. Never force-push, amend pushed commits, or push directly to main. Push the current feature branch if needed, using the repository's configured credentials (initialize keychain if required), then run `gh pr create --draft --title "<title>" --body-file "<repo-root>/.scratch/pr-drafts/<NAME>.md"`. Do not delete the draft automatically; clean it up only with the user's approval. Report the PR URL and any verification gaps. If repository guidance requires PR-check monitoring, follow it after creation.
